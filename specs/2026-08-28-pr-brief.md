## Problem & why

A reviewer opens a pull request and has no short answer to *"what does this PR
do, why, how risky is it, and what should I read first?"*. The raw material
already exists but scattered across surfaces: the derived **intent**
(`pr_intent`), the **blast radius** (changed symbols / callers / endpoints),
per-file diff statistics (`pr_files`), the linked GitHub issue, and the metrics
of the review run itself. Nothing fuses them into one orientation surface.

Today the Overview tab is a two-column grid — `IntentCard` + PR description on
the left, `BlastRadiusCard` on the right. There is **no** brief block, hard-coded
or otherwise; this feature adds one rather than replacing a placeholder.

**PR Brief** is a generated, cached, model-authored `Brief` produced **as a
consequence of a completed review run** and rendered as **three blocks** on the
Overview tab:

1. **PR Brief card** (full width, top) — `what` / `why` / `risk_level`, fused
   with the metrics of the run that produced it (verdict, score, findings,
   blockers, cost, tokens).
2. **Risk Areas** — an accordion *inside* the existing Intent card: concrete
   risks with a `kind` icon, a title, clickable file references, and an
   expandable explanation. It replaces the current flat `risk_areas` chip list.
3. **Review Focus** — a full-width "read these first" list below the
   Intent / Blast grid and above the PR description: each entry is a clickable
   file reference plus a short label, jumping straight into the Files Changed
   tab at that file and line.

Because generation is tied to run completion, the Brief and the review metrics
always exist together: there is no state in which a Brief is shown without a
verdict, and no state in which opening a PR page costs an LLM call. Before the
first completed run the Overview tab shows only an invitation to run a review.

The feature spans `@devdigest/shared` (both vendored copies), `server/` (a new
`modules/brief/`, one migration, edits to the intent module and to the run
completion flow), and `client/` (the Overview tab, the Intent card, and a new
deep-link navigation capability in the diff viewer).

## Goals / Non-goals

### Goals

- Brief generation as a **side effect of a review run reaching `done`**, from
  already-derived deterministic facts only (intent + blast summary + per-file
  diff statistics + linked issue), with **exactly one** structured LLM call per
  `(pr_id, head_sha)`, producing
  `Brief { what, why, risk_level, risks[], review_focus[] }`.
- A read route `POST /pulls/:id/brief` that serves the cached Brief for the PR's
  current `head_sha` and, with `force: true`, regenerates it — and nothing else:
  the route never generates implicitly.
- A structural grounding gate: every path in `risks[].file_refs` and
  `review_focus[].file_refs` is validated against the set of real paths known
  from the PR's changed files and the blast radius before the response reaches
  the client.
- The three UI blocks above, plus a new "open the Files Changed tab at a given
  file and line" navigation capability in the **normal** (non-Smart) diff view.
- Consolidation onto **one** risk model: the composed `PrBrief` type, the
  `Intent.risk_areas` field, its generation in the intent deriver, its line in
  the intent prompt rendering, and the `pr_intent.risk_areas` column are all
  removed — replaced by `Brief.risks[]`, not left as legacy.

### Non-goals

- **No generation from the client.** The Overview tab never triggers a first
  generation — neither on mount nor through a "Generate brief" button. The only
  two paths that call the model are run completion and an explicit
  force-regenerate of an already existing Brief.
- **No WhyTimeline / git-why** — a later, separate spec.
- **No diff bodies / hunks** in the LLM input.
- **No Project Context Folder as a Brief input.** The `context` module *does*
  exist on this branch (`server/src/modules/context/`, specs
  `2026-08-26-project-context-folder.md` and
  `2026-08-27-project-context-folder-authoring.md`) and already feeds
  `.devdigest/**` documents into the review prompt as untrusted
  `## Project context`. This iteration deliberately does **not** read it: the
  Brief's input set stays intent + blast + `pr_files` + linked issue. Feeding
  Context Folder documents into the Brief prompt and into the grounded path set
  is a separate follow-up spec, not an omission to be filled in during
  implementation.
- **No Smart Diff dependency.** Server-side Smart Diff does not exist —
  classification is entirely client-side and glob-based, and the
  `SmartDiff` / `SmartDiffFile.pseudocode_summary` contracts are defined but
  unused. Diff statistics in the Brief input are **flat per-file
  additions/deletions from `pr_files`**, not role-grouped (core / wiring /
  boilerplate).
- **The diff viewer's parsing, rendering, Smart Diff classification, and the
  review pipeline's own logic are not changed.** What *is* added to the diff
  viewer is navigation infrastructure only: per-file / per-line DOM markers, a
  pending-scroll state, and a transient highlight, mirroring the existing
  findings deep-link pattern. What is added to the run flow is one post-
  completion hook, not a change to how a review is produced or scored.
- No new model configuration — the `risk_brief` `FeatureModelId` is already
  registered in `FEATURE_MODELS`.
- The review metrics (findings / blockers / score / cost / tokens / verdict) are
  **not** copied into the `Brief` schema — they stay on `RunSummary` and the
  review record.
- **Accessibility is out of scope for this project** — no focus-management,
  screen-reader, or keyboard-navigation requirements.
- No executable tests are authored by this spec — unit / integration /
  `e2e/*.flow.json` are created in a separate pass.

## User stories

- **US-1**: as a reviewer, I want a one-glance summary of what a PR does and
  why, so that I can decide where to start reviewing.
- **US-2**: as a reviewer, I want a risk level and concrete risks tied to real
  files, so that I do not miss dangerous changes.
- **US-3**: as a reviewer, I want to click a file reference and land on that
  file and line in the diff, so that I do not hunt for it manually.
- **US-4**: as a reviewer, I want a dedicated regenerate control, so that I can
  refresh the Brief without re-running a whole review.
- **US-5**: as a reviewer, I want opening or re-opening a PR to cost nothing and
  render instantly, so that browsing PRs never spends model budget.
- **US-6**: as a reviewer, I want the review outcome (verdict, score, findings,
  blockers, cost, tokens) in the same card as the summary, so that I do not
  switch tabs to learn whether the PR passed.
- **US-7**: as a maintainer of this codebase, I want exactly one risk model in
  the contracts and the database, so that two competing "risk" surfaces do not
  drift apart.

## Acceptance criteria (EARS)

### Server — generation

- **AC-1 (US-1) — Verification: server-integration**: WHEN a review run for a PR
  reaches status `done`, the system shall — as part of that completion flow, not
  in response to any client request — assemble its input from the derived
  intent, the blast-radius summary, per-file diff statistics (`path`,
  `additions`, `deletions`) and the linked issue if any, perform exactly one
  structured LLM call using the `risk_brief` feature model, apply the grounding
  gate, and persist the resulting `Brief` against the PR's `head_sha`.
- **AC-2 (US-1) — Verification: server-unit**: The system shall never include
  diff bodies or hunks in the LLM payload — the payload shall consist
  exclusively of derived facts (intent text, blast summary, per-file
  addition/deletion counts, issue metadata).
- **AC-3 (US-1) — Verification: server-unit**: IF the assembled LLM input
  exceeds `MAX_INPUT_TOKENS` (8000), THEN the system shall truncate the
  lowest-priority sections first — linked-issue body, then blast summary, then
  diff statistics, then intent — so that the final payload does not exceed
  `MAX_INPUT_TOKENS`.
- **AC-4 (US-2) — Verification: server-unit**: WHEN the model returns a
  `risks[].file_refs` or `review_focus[].file_refs` entry whose file path is not
  a member of the known-path set (the union of the PR's `pr_files` paths and the
  blast-radius paths), the system shall drop that reference before persisting.
  The check is on the file path only, never line-precise.
- **AC-5 (US-2) — Verification: server-unit**: IF, after the grounding filter, a
  `review_focus` item has no surviving `file_ref`, THEN the system shall drop
  that item; a `risks` item whose `file_refs` became empty the system shall
  keep, with `file_refs: []` (the explanation has value without a link).
- **AC-6 (US-6) — Verification: server-integration**: IF the Brief LLM call,
  grounding, or persistence fails during run completion, THEN the review run
  shall still complete normally with its findings and metrics intact, nothing
  shall be persisted for the Brief, and the PR shall simply have no Brief —
  Brief generation shall never block, fail, or alter a review run.
- **AC-7 (US-5) — Verification: server-integration**: WHILE a Brief generation
  for a given `(pr_id, head_sha)` is in flight, the system shall not start a
  second one — generation is serialized by a Postgres advisory lock keyed on
  `pr_id`, and the cache is re-checked inside the lock. WHERE one review request
  fans out to several agents, exactly one Brief LLM call shall result.
- **AC-8 (US-6) — Verification: server-integration**: WHEN a Brief is generated
  during a batch of runs, the system shall attribute its tokens and cost to
  exactly one run — the run whose completion performed the generation — and
  every other run in the batch shall show no Brief cost, mirroring the intent
  layer's cost-attribution rule.
- **AC-9 (US-7) — Verification: architecture-review**: The Brief application
  service shall depend only on inward-facing interfaces (its repository port,
  the intent and blast read paths, the `LLMProvider`) and shall not accept the
  DI `Container` or import `db/schema`, `db/client`, or a concrete adapter.

### Server — reading and regenerating

- **AC-10 (US-5) — Verification: server-integration**: WHEN a client sends
  `POST /pulls/:id/brief` without `force` and a cached Brief exists whose
  `head_sha` equals the PR's current `head_sha`, the system shall return that
  Brief and shall make no LLM call.
- **AC-11 (US-5) — Verification: server-integration**: IF no Brief is cached for
  the PR, or the cached Brief's `head_sha` differs from the PR's current
  `head_sha`, THEN `POST /pulls/:id/brief` without `force` shall respond `200`
  with `{ brief: null }` — never a `404`, and never an implicit generation. A
  Brief for the new `head_sha` appears only when the next review run completes.
  (The `{ brief: null }` shape mirrors `GET /pulls/:id/intent`'s
  `{ intent: null }` convention, so callers need no special case.)
- **AC-12 (US-4) — Verification: server-integration**: WHEN a client sends
  `POST /pulls/:id/brief` with `force: true`, the system shall perform exactly
  one new LLM call over the same deterministic facts, overwrite the cached row
  under the PR's current `head_sha`, and shall not start a review run.
- **AC-13 (US-4) — Verification: server-integration**: IF a forced regeneration
  fails, THEN the system shall respond with a deterministic error
  (`5xx { error }`, no stack trace in the body) and shall leave the previously
  cached Brief unchanged.

### Server — one risk model

- **AC-14 (US-7) — Verification: server-integration**: After this feature,
  `GET /pulls/:id/intent` shall not return a `risk_areas` field, and the
  `pr_intent.risk_areas` column shall have been dropped by a migration.
- **AC-15 (US-7) — Verification: server-unit**: The intent deriver's structured
  output schema shall not request `risk_areas`, and the string the server renders
  into the review prompt for the intent slot shall contain no `Risk areas:` line.
  This is a deliberate, accepted removal of that signal from the review prompt
  (see *Non-functional → Accepted regression*).
- **AC-16 (US-2) — Verification: server-unit**: `Risk.kind` shall accept only
  the `RiskAreaKind` enum (`security | dependency | performance | data |
  api_change | other`); a `Risk` whose `kind` falls outside the enum shall be
  rejected by contract validation.
- **AC-17 (US-7) — Verification: architecture-review**: The composed
  `PrBrief { intent, blast, risks, history }` type shall be removed from both
  vendored copies of `@devdigest/shared` and from the client's re-export surface,
  and no code shall reference it afterwards.

### Client — the three blocks

- **AC-18 (US-1) — Verification: client**: WHEN a Brief for the PR's current
  `head_sha` has loaded on the Overview tab, the client shall render the PR
  Brief card as a full-width block above the Intent / Blast grid, showing `what`
  and `why`, and shall render `risk_level` as a coloured vertical accent rail on
  the card's leading edge plus a small textual level label — `high` = red,
  `medium` = amber, `low` = green. The rail and the verdict icon box (AC-19)
  coexist and are never merged: the icon box states the **review's verdict**,
  the rail states the **Brief's model-assessed risk level**.
- **AC-19 (US-6) — Verification: client**: The PR Brief card shall show, sourced
  from the completed run that produced the Brief and its review record: the
  verdict icon box and label, a `{findings_count} findings · {blockers} blockers`
  badge, a circular score ring rendering `score`, and a `$ {cost_usd}` +
  `{tokens_in}→{tokens_out}` row. These values shall come from `RunSummary` and
  the review record, never from `Brief`.
- **AC-20 (US-6) — Verification: client**: IF the completed run's `score` is
  `null`, THEN the score ring shall render an explicit unknown state — an empty
  ring with `N/A` in its centre — the remaining metrics shall still render, and
  the card's layout shall not shift relative to the scored case.
- **AC-21 (US-6) — Verification: client**: IF no Brief exists for the PR's
  current `head_sha`, THEN the Overview tab shall render no PR Brief card, no
  Risk Areas section and no Review Focus block, and shall instead show a nudge
  inviting the user to run a review, whose control triggers the **same**
  run-review action as the page-header button rather than a duplicate of it.
- **AC-22 (US-2) — Verification: client**: WHEN the Brief has a non-empty
  `risks[]`, the client shall render a Risk Areas accordion inside the Intent
  card, below the in-scope / out-of-scope columns, where each row shows an icon
  chosen by `risk.kind`, `risk.title`, and clickable `risk.file_refs`, and
  expanding a row reveals `risk.explanation`. `risk.severity` shall not be
  rendered in this card.
- **AC-23 (US-1) — Verification: client**: WHEN the Brief has a non-empty
  `review_focus[]`, the client shall render a full-width "REVIEW FOCUS — READ
  THESE FIRST" block with a count badge, positioned below the Intent / Blast
  grid and above the PR description, where each item renders a bullet, its
  clickable `file_refs` in shortened monospace, a `—` separator, and `label`.

### Client — deep link into the diff

- **AC-24 (US-3) — Verification: client**: WHEN the user activates a `file_ref`
  in Review Focus or in a Risk Areas row, the client shall navigate the PR page
  to `?tab=diff&file=<path>&line=<n>` in a **single** navigation that preserves
  all other existing query parameters, where `<n>` is the reference's line — for
  a range reference such as `src/api/users.ts:12-18` the first line (`12`) — and
  `line` is omitted entirely when the reference carries no line.
- **AC-25 (US-3) — Verification: e2e**: WHEN the PR page renders the Files
  Changed tab with a `file` query parameter naming one of the PR's changed
  files, the client shall bring that file's card into view, expand it if it is
  collapsed, and apply a visible highlight to it; WHERE a `line` parameter is
  also present, the highlight shall target that line within the file. This shall
  work in the normal diff view, independently of Smart Diff mode.
- **AC-26 (US-3) — Verification: client**: WHEN the highlight has been applied,
  the system shall clear it after a fixed timeout of 2–3 seconds, and shall
  leave `file` and `line` in the URL — the deep link stays shareable and a
  reload reproduces the same scroll position.
- **AC-27 (US-3) — Verification: client**: IF the `file` query parameter names a
  path that is not among the PR's changed files, THEN the Files Changed tab
  shall render normally with no scroll, no highlight, and no error state.
- **AC-28 (US-3) — Verification: client**: WHILE the deep-link target is
  unresolved because its file card has not yet mounted, the client shall retain
  the pending target and apply the scroll and highlight once the card mounts,
  rather than dropping the request.

### Client — regenerate, loading, errors

- **AC-29 (US-4) — Verification: client**: WHERE a PR Brief card is rendered,
  the client shall offer a regenerate control on that card, visually and
  functionally distinct from the page-header Run Review button; activating it
  shall send `POST /pulls/:id/brief` with `force: true` and shall not start a
  review run. Where no Brief card is rendered (AC-21), no regenerate control
  shall be offered.
- **AC-30 (US-5) — Verification: client**: WHILE the cached-Brief request or a
  regeneration is in flight and no Brief has rendered yet, the client shall show
  a loading state consistent with the Intent card's "Recalculating…" affordance
  and shall disable the regenerate control; IF the request fails, THEN the
  client shall show a "Failed to load PR Brief" error state in the style of the
  Blast Radius card's error boundary, keep the card mounted, and offer retry
  through the same regenerate control.

## Edge cases

- **No completed run yet** — the ordinary state of a freshly imported PR. No
  Brief, no Risk Areas, no Review Focus; only the run-review nudge (AC-21).
- **Run failed or cancelled** — generation is tied to `done` only (AC-1), so no
  Brief is produced and the nudge remains.
- **Stale Brief after a new commit** — a cached Brief whose `head_sha` no longer
  matches the PR reads as absent (AC-11): the card disappears and the nudge
  returns until the next review run completes. Because no card is rendered, no
  regenerate control is offered either — this deliberately prevents producing a
  Brief for the new `head_sha` while the visible metrics still belong to a run
  on the old one.
- **`head_sha` refreshed without a new commit** — `GET /pulls/:id` re-fetches
  `body` and counts from GitHub without touching `head_sha`, so this does not
  invalidate the Brief. Accepted: a change in diff statistics under an unchanged
  `head_sha` is not reflected until the next completed run or a manual
  regenerate.
- **0 risks** — `risks[]` empty → the Risk Areas section is hidden entirely, not
  rendered as an empty accordion (this preserves the behaviour
  `specs/pr-intent-layer.md` required for the chip list it replaces).
- **0 review_focus** — none produced, or all dropped by grounding → the Review
  Focus block is hidden.
- **All file refs hallucinated** — after grounding every `review_focus` item is
  dropped and every risk keeps its explanation with `file_refs: []`; the card is
  still informative (`what` / `why` / `risk_level` / metrics).
- **No linked issue** — the issue section is absent from the input; a normal
  path, not an error.
- **Blast radius degraded** (`status: "degraded"`, `blast: null`) — the
  known-path set narrows to the PR's `pr_files` paths alone; grounding does not
  fail, it filters harder. *Accepted risk: under a degraded blast, some
  otherwise-valid references may be dropped.*
- **PR with no `pr_files` rows** — the known-path set is empty, so every file
  reference is dropped. The Brief renders as `what` / `why` / `risk_level` plus
  risk explanations with no clickable references, and **no "ungrounded" marker
  is shown** — silently link-free is the intended presentation.
- **Completed run with `score: null`** — the ring renders its unknown state
  (AC-20); the rest of the metrics row is unaffected.
- **Batch of several agents on one PR** — exactly one Brief LLM call, attributed
  to one run (AC-7, AC-8).
- **File reference without a line** (e.g. `package.json`) — navigation targets
  the file only; no `line` parameter, no line highlight (AC-24, AC-25).

## Data model and migrations

**`Brief`** — the model output, cached once per PR:

| Field | Type | Notes |
|---|---|---|
| `what` | `string` | one sentence, what the PR does |
| `why` | `string` | 1–2 sentences, motivation |
| `risk_level` | `"low" \| "medium" \| "high"` | drives the card's accent rail colour (AC-18) |
| `risks` | `Risk[]` | may be empty |
| `review_focus` | `ReviewFocusItem[]` | may be empty |

**`Risk`** narrows the existing contract: `kind` becomes the `RiskAreaKind` enum
(AC-16) instead of a free string; `title`, `explanation`, `severity`, and
`file_refs` are unchanged. **`ReviewFocusItem`** is new:
`{ label: string, file_refs: string[] }`.

**Cache** — the existing `pr_brief` table (primary key `pr_id`, FK to
`pull_requests` with `ON DELETE CASCADE`) is reused. The stored row holds the
generated `Brief` plus the `head_sha` it was generated under; there is no Brief
history — a new generation overwrites the row.

**Migration steps**, in this order, shipped as ordinary numbered migrations run
through `pnpm db:migrate` (never on boot):

1. `DELETE FROM pr_brief` — the table currently holds the dead composed
   `PrBrief` JSON, which has no `head_sha` and no relationship to the new
   contract. It is removed outright rather than left to be overwritten lazily.
2. `ALTER TABLE pr_brief ADD COLUMN head_sha text NOT NULL` — safe because the
   table was just emptied, so no backfill default is needed.
3. `ALTER TABLE pr_intent DROP COLUMN risk_areas` (AC-14).

Both changes are destructive to existing data and are irreversible in place.

## Non-functional

- **Cost / perf — Verification: server-unit**: The system shall keep the
  assembled LLM payload at or below `MAX_INPUT_TOKENS` (8000) — see AC-3.
- **Cost — Verification: server-integration**: Opening or re-opening a PR page
  shall never cause an LLM call. The only two paths that call the model are run
  completion (AC-1) and an explicit forced regeneration (AC-12).
- **Security — Verification: server-unit**: The system shall pass all external
  text (PR body, linked-issue body, derived intent text) to the model as data,
  not as instructions — see *Untrusted inputs*.
- **Reliability — Verification: server-integration**: Brief generation shall
  never block, fail, or alter a review run (AC-6), and a failed generation shall
  never persist a partial Brief.
- **Accepted regression — Verification: manual-qa**: Removing
  `Intent.risk_areas` (AC-15) deletes the `Risk areas:` line from the intent
  context passed to the review prompt. This is a deliberate loss of a prompt
  signal, accepted in exchange for a single risk model; if review quality
  measurably regresses, the replacement is to feed `Brief.risks[]` into the
  review prompt in a follow-up spec, not to reinstate `Intent.risk_areas`.

## Inputs (provenance)

| Input | Source | Kind |
|---|---|---|
| generation trigger | a review run reaching `done` | [reused: the existing run completion flow] |
| intent text (`intent`, `in_scope`, `out_of_scope`) | intent module (`pr_intent`) | [reused: pr-intent-layer] deterministic, cached by `head_sha` |
| blast summary + blast file paths | blast module (`PrBlastResponse`) | [reused: blast-radius] deterministic, live |
| per-file diff statistics (`path`, `additions`, `deletions`) | `pr_files` | [deterministic: DB aggregate, no model] |
| linked issue (`number` / `title` / `body`) | the PR body → GitHub | [deterministic: fetched, optional] |
| known-path set for grounding | union of `pr_files` paths and blast paths | [deterministic: derived from the two above] |
| `Brief { what, why, risk_level, risks[], review_focus[] }` | one `risk_brief` LLM call | new — the only model output in this feature |
| review metrics (verdict / findings / blockers / score / cost / tokens) | the completed run — `RunSummary` + the review record | [reused: findings-severity-breakdown] never part of `Brief` |

## Untrusted inputs

The Brief prompt carries text this system does not control: the **PR body**, the
**linked issue body**, and the derived **intent text** (itself derived from the
PR body). All of it shall be wrapped and marked as untrusted data before the LLM
call, using the same shared injection guard the review prompt already applies to
`pr_description` and `## Project context`, so that text authored inside a PR or
issue cannot redefine the Brief-generation instructions. Denylists, regex
scanning, and keyword filtering of untrusted text are forbidden by repo
convention — the injection guard is the only defence.

The model's output is untrusted in the other direction as well:

- **File references are not trusted.** `reviewer-core`'s `groundFindings()` is
  not applicable here — it needs diff hunks, which this input deliberately does
  not carry — so a lightweight path-set gate is used instead (AC-4 / AC-5):
  membership in the union of `pr_files` and blast paths, with no line precision.
- **The `file` query parameter is model-influenced and user-editable**, and
  under AC-26 it persists in shareable URLs. It shall be consumed purely as a
  lookup key against the already-loaded set of changed files; an unmatched value
  is a no-op (AC-27). It shall never be used to construct a filesystem path, a
  fetch URL, or an `href`.
- `what`, `why`, `title`, `explanation`, and `label` are model-authored strings
  rendered as text. They shall not be rendered as raw HTML, and any file
  reference rendered as a link shall navigate only within this app's own PR
  route — never to an arbitrary URL derived from model output.

## Module interactions

The new `brief` module is an application-ring service in `server/src/modules/`.
It is invoked by the review run completion flow, reads other modules through
their service interfaces, and mutates none of them. Its repository (the
`pr_brief` cache and the advisory lock) is infrastructure behind a port; the
route is the only entry-ring piece and is read/regenerate only.

| From | To | Contract / direction | If the other side fails |
|---|---|---|---|
| review run completion | `brief` service — generate for `(pr_id, head_sha)` | in-process, fire-and-forget within the completion flow | AC-6: the run completes anyway, no Brief persisted |
| `brief` service | intent read path (`pr_intent` for the PR) | in-process, read-only | missing intent → that section is omitted; generation continues |
| `brief` service | blast read path (per-PR resolver) | in-process, read-only; also supplies grounded paths | `degraded` → known-path set narrows to `pr_files` alone |
| `brief` service | pulls — `pr_files` (`path`, `additions`, `deletions`) | in-process, read-only | empty → no grounded paths, links suppressed silently |
| `brief` service | pulls — linked issue from the PR body | in-process, read-only, optional | fetch failure → issue section omitted, not an error |
| `brief` service | `LLMProvider` (`risk_brief` feature model) | port, exactly one `completeStructured` call | AC-6 on the run path, AC-13 on the force path |
| `brief` service | `pr_brief` cache (repository port) | read / upsert, serialized by an advisory lock on `pr_id` | write failure → nothing persisted, no partial row |
| `client` | `POST /pulls/:id/brief` | HTTP; read cache, or regenerate with `force` | AC-30 error state, card stays mounted, retry via regenerate |
| `client` | `GET /pulls/:id/runs` + the review record | HTTP, read-only | no completed run → AC-21 nudge, no Brief blocks |
| `client` Overview blocks | `client` PR page query state | one batched navigation writing `tab` / `file` / `line` | unmatched `file` → AC-27 no-op |

## Proposed UX improvements

*Proposals, not decisions — none of these were in the reference design.*

- **Mark visited Review Focus / Risk references.** The Review Focus block is a
  worklist; without visited state a reviewer loses their place after each jump
  into the diff and back. Closes the "no feedback after acting" gap.
- **A back affordance from the diff to the Brief.** AC-24 is a one-way jump; the
  reviewer's only way back to the worklist is the Overview tab button, which
  loses the position in the list. Closes a flow gap the design does not address.
- **Show `risk.severity` as an ordering signal even though it is not rendered as
  a badge (AC-22).** Sorting the accordion by severity costs no UI surface and
  makes the highest-severity risk the first thing read. Closes the gap where the
  contract carries a severity the UI throws away entirely.
- **Surface staleness rather than hiding the Brief.** Under AC-11 a new commit
  makes the Brief vanish until the next review; a "this Brief describes an older
  commit" state would lose less context than showing nothing. Deliberately not
  specified here because it would put stale metrics back on screen — recorded as
  the obvious follow-up if the disappearing card proves confusing.
