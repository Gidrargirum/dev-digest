# Development Plan — PR Brief

**Spec:** `specs/2026-08-28-pr-brief.md`
**Date:** 2026-08-28
**Decisions locked in:** (1) колонка `run_id` на `pr_brief` з `ON DELETE SET NULL`;
(2) `DELETE FROM pr_brief` дописується руками у згенеровану міграцію як свідоме
відхилення; (3) чужий/неіснуючий `pr_id` → `404` на обох шляхах роуту.

## Execution mode

- **Multi-agent**: `implementer #1` (сервер + контракти + деструктивні міграції) →
  `implementer #2` (клієнт) → `architecture-reviewer`. Тести — окремим запитом
  пізніше (`api-test-writer` / `ui-test-writer`).
- Порядок строгий: #2 стартує лише після зеленої секції A, бо контракти в обох
  копіях `vendor/shared` мають існувати до того, як клієнт на них посилатиметься.

## Scope

- Пакети: `server/`, `client/`, обидві копії `@devdigest/shared`.
- **Поза скоупом**: `reviewer-core/`, `mcp/`, `e2e/`; авторство нових тестів
  (спека, *Non-goals*); Project Context Folder як вхід Brief; Smart Diff;
  WhyTimeline; чотири «Proposed UX improvements» зі спеки; будь-які зміни
  `specs/*.md`.
- Наявні тести, що посилаються на поле, яке видаляється, правляться **мінімально**
  — це умова зеленого гейта, а не тестовий прохід (кроки 1.7, 2.7).

## Recommendations

- **Переюзати `vendor/ui/primitives/CircularScore.tsx`** для кільця score.
  Компонент вимагає `score: number`, а AC-20 просить порожнє кільце з `N/A`;
  `vendor/ui` не редагується, тож unknown-стан рендериться власною гілкою в
  `PrBriefCard`, а `CircularScore` викликається лише при `score != null`. Чисте
  покращення, закладено в крок 2.3.
- **Не переюзати `groundFindings()`** з `reviewer-core` — спека прямо каже, що він
  потребує diff-ханків, яких у вході Brief немає.
- **`run_id` як `ON DELETE SET NULL`, не `CASCADE`.** `agent_runs` реально
  видаляються (`useDeleteRun` у клієнті), і видалення run не повинно нищити Brief
  — тож `run_id` nullable, а клієнт має fallback (крок 2.3 і *Risks*).

## Risks

- **Ручна правка згенерованої міграції** (рішення #2) — `routing.md` класифікує це
  як finding, і `pr-self-review` підніме його. Мітигація: прийнято свідомо,
  `implementer #1` називає файл і причину у звіті (крок 1.2), щоб находка була
  очікуваною й аргументованою. Ризик, що лишається: наступна `db:generate` над
  цією ж таблицею може згенерувати diff відносно snapshot'а, який не знає про
  ручний `DELETE` — але `DELETE` не є DDL, тож snapshot він не змінює.
- **`run_id` nullable** — прямий наслідок `ON DELETE SET NULL` плюс форс-регенерація.
  Отже, шлях «є Brief, run_id порожній» не екзотика, а штатний стан → мітигація:
  явний fallback у кроці 2.3.
- **Метрики й Brief можуть розійтися після force-регенерації**: `what`/`why`/`risks`
  уже нові, а метрики на картці — від старого `done` run. AC-19 цього випадку не
  описує. Прийнято: спека дозволяє force лише коли картка вже показана.
- **`server/src/modules/index.ts`, `client/src/lib/types.ts`, `client/messages/en/**`
  поза матрицею `routing.md`** → перші два ревʼюяться лише
  `security`+`typescript-expert`, третій нічим. Відома дірка матриці →
  `pr-self-review` має назвати її у звіті.
- **Деструктивна міграція незворотна.** `pr_brief` містить мертвий composed-JSON,
  який ніхто не читає — втрата змістовно нульова. `pr_intent.risk_areas` — реальна
  втрата сигналу, вже прийнята спекою (*Accepted regression*); відкат = наступна
  спека, що подає `Brief.risks[]` у review-промпт.
- **Клієнтські гейти червоні між A і B** — очікуваний стан передачі;
  `implementer #1` зобовʼязаний написати це у звіті.
- **Інтеграційний гейт вимагає Docker** — без нього саме нова частина (advisory
  lock, upsert з `run_id`, DROP COLUMN) лишається неперевіреною → підняти Postgres
  до кроку 1.2, він там усе одно потрібен.
- **`drizzle-kit` може стати інтерактивним** (`server/insights/INSIGHTS.md`,
  2026-08-13) → дві таблиці змінюються в різні боки, промпту не має бути; якщо
  зʼявиться — два проходи генерації.
- **Advisory lock — новий патерн** (`grep pg_advisory` по `server/src` порожній):
  немає прецеденту, і lock тримається довше за LLM-виклик. Прийнято: AC-7 вимагає
  серіалізації, `BRIEF_TIMEOUT_MS` обмежує вікно; альтернатива (lock поза
  транзакцією) вимагає ручного unlock у `finally` і гірше переживає падіння
  процесу.
- **`404` розходиться з `GET /pulls/:id/intent`** (рішення #3): два сусідні
  PR-роути тепер по-різному відповідають на чужий `pr_id`. Мітигація: розбіжність
  зафіксована в `modules/brief/README.md` (крок 1.5). Побічний ефект — `404` на
  brief підтверджує неіснування PR, чого intent-роут навмисно не робить; для
  локального однокористувацького інструменту це прийнято.
